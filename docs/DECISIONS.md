## 2026-07-27 ユーザビリティテストの操作を小窓に一本化
- 決定: 案A（小窓に全部集約）。serviceモードで、録画開始・サービスを開く・達成/できなかった・セッション終了を、すべて右下の小窓（Document PiP）に集約する。メイン画面のタスクカードからは重複操作ボタンを外し、「操作は右下の小窓で」という案内と、詰み防止用の「小窓を再度開く」だけを残す
- 却下: 案B（メイン画面に集約）— サービスを別タブで開くとメインが背面に回り、操作のたびにタブを戻す必要が出るため
- 却下: 案C（2箇所併記のまま番号ステップ化）— ボタンの重複自体が残り、根本解決にならないため
- 理由: 操作の起点が割れていた（録画開始=小窓 / サービス起動=メイン / 達成・終了=両方に重複）ため、参加者がどこを見て操作すればいいか分からないという指摘
- 補足: サービス起動を小窓側の実リンク(a target)に移すため、Document PiP の iframe 内からの別タブ起動が実機で機能するか検証が必要
- 追加調整(2026-07-27): (1)メイン画面は通常時はタスク文言も進捗も出さず「小窓を見て操作してください」の案内＋再オープンのみ（タスク文言は小窓に一本化）。(2)小窓は黒い主CTAが常に1つだけになるよう段階表示（録画→サービス→達成/できなかった）。serviceOpened state で遷移。(3)①②③の番号は廃止。(4)「セッションを終了」だけは録画/サービス前でも押せる脱出口として常時表示（詰み防止。レビュー指摘を反映）
- 追加調整その2(2026-07-27): (5)小窓のタスク文言も事前手続き完了後にのみ表示（readyForTask=録画済み&&(サービス開いた||URL無)）。準備中は「準備」案内を出す。(6)メイン画面に3ステップ進捗（①録画 ②サイトアクセス ③テスト開始）を追加。小窓→メインへ BroadcastChannel で recording_started / service_opened を送り現在地を進める

## 2026-07-28 過去セッションの回答を文字起こしから復元
- 背景: 比較テーブルを本番に出したが、リサーチャーの画面には何も表示されなかった。Answer テーブル導入（2026-07-28）より前に実施したセッション（5〜7月分）は回答が文字起こしにしか無く、`answeredCount === 0` で黙って非表示になっていた
- 決定:
  1. テーブルが空のときは黙って消えず、理由の説明＋抽出ボタンを出す。テーブル表示中も「未取得 N 件を抽出」の導線を残す（1件でも埋まるとボタンが消えて残りを埋められなくなるため）
  2. `POST /api/interviews/[id]/backfill-answers` で文字起こしから質問ごとの回答を AI 抽出（`extractAnswersFromTranscript`）。深掘りは元の質問にまとめる
  3. **既存行は絶対に上書きしない**（`createMany` の `skipDuplicates`）。実施中セッションも対象外にする。実施中は被験者側が本物の回答を書き込むため、AI の再構成で置き換わる競合を避ける
  4. スコア質問（rating/nps）は文字起こしの「4（4 / 5）」から数値を復元する。取れない場合はその質問を諦める（スコアの枠にテキストを入れない）
  5. 1回5件・時間予算210秒で打ち切り、残件を返す。504 でも保存済み分を反映するため必ず再読み込みする
- あわせて修正: AI 要約が英語で出ていた（プロンプトに言語指定が無かった）。summary/themes/sentimentNote を日本語指定に。themes は分割処理があるため半角カンマ区切りを明示
- 注意: 変更前に分析済みのセッションは英語の要約・テーマが残る。テーマ横断集計は再分析するまで英語版と日本語版に分かれてカウントされる

## 2026-07-28 質問×被験者の回答比較テーブル
- 背景: 「質問1を肯定的に回答した人／そうでない人を見分けたい」。深掘り質問は人によって個数が違うが、元の質問に紐づいているはず、という指摘
- 前提の確認: 深掘りの回答は `recordOpenAnswerIfAny` が元の質問の Answer 1件にまとめて保存している（questionId で紐づく）。したがって列は人によって増減しない
- 決定: インタビュー詳細に「回答の比較（質問 × 参加者）」テーブルを追加。行=参加者・列=質問。参加者列は固定、列ヘッダで並び替え、回答本文での絞り込み、スコアは色分け、長文は展開
  - セルの対応づけは questionId が第一キー（質問を並べ替えても崩れない）。questionId を失った回答は文言で拾うが、1件の回答を複数列に出さないよう2周に分けて割り当てる
  - スコアの色分けは、NPS だけ標準区分（推奨者9-10／中立者7-8／批判者0-6）に合わせる。単純な比率だと 8 が肯定的に見え、同じ画面の NPS 集計と食い違うため
  - `Answer.followUpCount` を追加。発話数から数えると「深掘りされたが答えなかった」分が抜けるため、AI 側のカウンタ（followUpCountRef）の値を保存する
- 追記(2026-07-28): 自由回答にも AI 判定を追加（案B を選択）。`Answer.sentiment` に positive/neutral/negative を保存し、テーブルでバッジ＋色帯表示・判定順ソート・「肯定的」等での絞り込みに対応
  - 文字起こし分析とは**別の AI 呼び出し**にした（同じ呼び出しに混ぜると上限超過で要約まで壊れた前例があるため）。判定が失敗しても要約・テーマは無傷
  - 判定は「評価対象への態度」を見る（一般的な機嫌ではない）。AI 判定である旨を画面に明示し、参考値として扱う
  - 応答のパース失敗は「判定なし」ではなく**失敗として投げる**。同一視すると既存の判定を全件 null で上書きしてしまうため
  - 判定処理は `status: 'done'` の**後**に置く。前に置くと、ここで落ちたときに status が processing のまま固まり、画面から再分析できなくなる

## 2026-07-28 パイロット実行と所要時間の自動算出（UXレビュー P2 残り）
- **パイロット実行**: `Session.isPilot`。リサーチャーが本番データを汚さず被験者フローを試せる入口（`POST /api/interviews/[id]/pilot`、editor 以上）。認証必須にしたのは、被験者が自分のセッションをパイロットと自称して集計から抜ける＝データを消せる状態を作らないため
  - 除外は5経路すべてに適用: 横断検索 / CSVエクスポート / 共通インサイト / AIチャットの文脈 / ダッシュボードのセッション件数。加えてクライアント側の定量集計・タグ集計・レーダーからも除外
  - 一覧・詳細には「パイロット」バッジを出して残す（消したくなったら既存の削除APIで消せる）
- **所要時間の自動算出**: 参加ページの「約15〜30分」固定表示を、設問構成（自由回答／スケール／タスク数／SEQ／事前質問）からの算出に置き換え。算出は `src/lib/duration-estimate.ts` に集約し、サーバー側で計算して返す（表示側にロジックを持たせない）。個人差を考慮して幅で提示し5分単位に丸める

## 2026-07-28 調査運用の基盤（UXレビュー P2）
- 決定: P2 の4点を実装
  1. **調査の編集機能**: PATCH /api/interviews/[id]。id が一致する質問・タスクは更新して残すため過去の回答との紐づけが切れない。削除しても回答側が文言スナップショットを持つので集計は壊れない。実施済みがある場合は「集計が混ざる」警告を出す
  2. **横断CSVエクスポート**: インタビュー単位で全セッションを1ファイルに（セッション/属性/タスク結果/回答/ハイライトのセクション構成）
  3. **共有リンクの有効期限**: Session.shareExpiresAt。発行時に日数指定（既定30日、0で無期限）。従来は無期限で、URLを知る誰でも永久に閲覧できた
  4. **SEQ（タスク直後の易しさ評価）**: Interview.seqEnabled で調査ごとに ON/OFF（既定は無効＝既存調査の進行を変えない）。TaskResult.seq に1〜7。小窓・メイン画面の全経路に対応
  5. **スクリーニング／属性**: ScreenerQuestion（選択肢＋参加不可条件）と ScreenerAnswer。足切り判定はサーバー側のみで行い、条件は被験者に返さない。対象外の場合はセッションも参加者も作らず、理由も伝えない。属性はセッションに紐づけてセグメント分析に使う
- 補足: 足切り理由を伝えないのは、設問の意図を推測されて回答を操作されるのを防ぐため（リサーチの標準的な作法）

## 2026-07-28 測定結果を構造化保存（UXレビュー P0）
- 背景: UXリサーチャー視点のレビューで「タスク成功率・NPS・所要時間が一切集計できない」と判明。タスク達成は文字起こしに `タスク1「…」→ 達成` という**文章1行**、評価は `9（9 / 10）` という**被験者の発言**として保存されており、結果を入れるテーブルが存在しなかった
- 決定: `TaskResult` / `Answer` テーブルを新設し、文字起こしとは独立に定量データを持つ。`Session.consentedAt` で同意の証跡も記録
  - 保存は `(sessionId, order)` をキーにした**行単位 upsert**。全置換にしない（並行送信での重複・巻き戻しを DB の unique 制約で防ぐ／途中リロードで既存結果を消さない）
  - UI: セッション詳細に「測定結果」（成功率・所要時間・スコア）、インタビュー詳細に横断集計（タスク別成功率バー・NPS・平均）。定量はAI分析の完了を待たないので `done` で絞らない
  - CSV は測定結果セクションを先頭に追加し、全列を数式インジェクション対策の `q()` 経由に
- 却下: 文字起こしテキストを正規表現でパースして集計 — 書式変更や再文字起こしで壊れるため
- 補足: 経過時間の基準を「開始ボタン押下時」にリセット。従来はマウント時基準でガイド滞在時間が所要時間に混入し、録画の再生位置ともズレていた（文字起こし・感情・録画の3つの原点が揃うようになった）
- 所要時間の計測開始（タスク1）: 事前手続きの時間を含めないよう、被験者が実際に着手できる時点まで遅らせる。service=小窓から `task_ready`（録画開始＋サイトを開いた時点）を受信時／prototype=画面選択ダイアログが閉じた後／小窓が開けなかったフォールバック=メイン画面の「サービスを開く」クリック時。タスク2以降は前タスクの終了時刻を開始時刻とする
- 残課題（UXレビューの P1 以降）: 文字起こしの全文検索、タグ付け/ハイライト、横断エクスポート、発言単位 sentiment の修正（現状は全体の1値を全発言にコピーしていて誤解を招く）、調査の編集機能

## 2026-07-27 顔フレーミング判定（テスト中の見切れアラート）
- 決定: 小窓のカメラ映像に対し、tiny_face_detector（既存 /models、約190KB）で2.5秒ごとに顔検出し、**「顔が写っていない」「顔が画面端で見切れている」の2つ**を検知したら小窓のカメラ下端に警告バナーを出す。判定・表示は小窓で行う（被験者が見ているのは常に最前面の小窓／背面タブは処理が間引かれ検出不安定なため）
- 却下: 距離（遠い/近い）も警告 — 閾値調整が要り誤検知が増えるため見送り
- 却下: 見切れ時間帯を結果に記録 — スコープ拡大のため今回はライブ警告のみ
- 補足: 感情分析用の faceExpressionNet は読まず tinyFaceDetector のみロード（軽量化）。見切れ=顔 boxが映像端±1.5%に接触で判定。補助機能なのでモデルロード失敗時も録画は継続
- 適用範囲拡大(2026-07-27): 小窓だけでなく全モードに適用。メイン画面のカメラ（プロトタイプ時=右下の小型PiP／通常インタビュー時=全画面）にも同じ警告を表示。メインは既存 useEmotionDetection の感情検出ループ（5秒ごと）から顔 box を算出して二重処理を回避（小窓は独立ルートなので2.5秒の専用ループ）。バナー位置はカメラ映像の位置（PiP/全画面）に追従

## 2026-07-28 prisma は db push 方式に統一（マイグレーション削除）
- 背景: schema.prisma は postgresql、`prisma/migrations` は sqlite という矛盾が未解決だった
- 実態調査: 残っていたマイグレーションはテーブル 7 個ぶんのみで、現在のスキーマ（17 モデル）を再現できない。lock も sqlite のまま。デプロイは `prisma db push --accept-data-loss`（build スクリプト）で行っており、マイグレーションは一切使われていなかった
- 決定: `prisma/migrations` を削除し、**db push 方式であることを schema.prisma の冒頭に明記**する。`prisma migrate` を実行すると失敗するか壊れた DB ができる罠だったため
- 却下: 稼働中DBから baseline を作って migrate 方式へ移行 — 動いている本番のデプロイ経路を変えるリスクが大きく、現状の運用規模に見合わないため。将来必要になった時点で baseline から始める
- 補足: `prisma/dev.db`（SQLite 時代の残骸）は .gitignore 済みでリポジトリには入っていない
