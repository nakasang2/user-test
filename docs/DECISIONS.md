## 2026-08-14 実施中に見つかった不具合4件の調査・対応
- 背景: ユーザーが実際にテストを実施した際、(1) 説明文が読まれずテンプレートが読まれる (2) ユーザビリティテストの事前質問が聞かれない (3) タスク1が読み上げられない (4) 事後質問時に「音声認識が中断しました」ダイアログが出る、の4件を報告
- 調査・対応:
  1. **説明文が読まれない**: 実際は「調査編集モーダルの保存が失敗していた」不具合。モーダルはヘッダー・フッター固定・本文のみスクロールする構造だが、保存失敗時のエラー（例:「事前質問に選択肢を入力してください」）がスクロール領域の最後にしか表示されておらず、説明文だけ編集してすぐ保存すると気づけないまま保存全体が失敗していた（説明文の変更も含めて未反映）。エラー表示を常に見えるヘッダー直下に移動して修正
  2. **事前質問が聞かれない**: 「パイロットテスト」機能特有の仕様。パイロット実行は参加者登録ページ（`/join`、名前・同意・事前質問を収集）を経由せず直接通話画面に入るため、事前質問は構造上表示されない（本番の参加者リンクからは正しく動作する）。**対応: 今回は保留し、仕様として記録するに留める**（ユーザー判断）。パイロットも `/join` を経由させる案は、実装規模がやや大きい（研究者自身が名前入力・同意チェックを通す必要がある）ことを理由に見送り
  3. **タスク1が読み上げられない**: 案内画面・スタート操作は正常だったと確認できたため、`/api/tts` への単発呼び出しの一過性の失敗（ネットワーク瞬断等）が原因と判断。リトライが無く、失敗時のトースト通知も小窓の隅で気づきにくかった。`/api/tts` 呼び出しを1回だけ自動リトライするよう修正
  4. **音声認識が中断したダイアログ**: `recognition.onerror` がエラー種別を問わず即座にダイアログを出し、再開処理も `onend` ハンドラも無い明確なコードのバグだった。事後インタビューは回答が長く続くため、ブラウザ側の連続認識の内部上限に達しやすい。意図した停止かどうかをrefで判定し、意図しない終了なら自動的に再開する（最大5回）よう修正。マイク権限拒否等の回復不能なエラーのみ即座に案内を出す
- 補足: 3・4はローカルの `OPENAI_API_KEY` がプレースホルダのため実際のAPI応答での動作確認はできず、コードレビューのみで本番反映した。次回実施時の実機確認が必要

## 2026-08-14 短すぎる回答への深掘りを強化
- 背景: スライド資料の内容を肉付けした流れで、ユーザーから「インタビュー・印象受容度テスト・ユーザビリティテストの3種類全てで、体験を聞いているのに一言で終わる回答が多く情報量が少なすぎる」との指摘
- 調査結果: 3種類のテストは全て同じ会話ループ（`InterviewRoom.tsx`）と同じ深掘り判断API（`/api/interviewer`）を共有しており、この1箇所の基準を直せば3種類すべてに効くと判明。深掘りするかどうかは完全にAI（gpt-4o）の毎ターム判断に委ねられており、文字数等の機械的な足切りは無い
- 決定: **A案（判断基準の反転）**。従来は「回答が短いだけで、内容としては答えになっている」場合は深掘りしない指示だったが、この一文を削除し、具体的なエピソード・比較・理由が伴わない一言回答は「具体的な欠落（＝エピソード・理由が語られていない）」として扱い、基本は深掘りする方針に変更
  - 却下: B案（反転＋文字数の機械的な下限も追加）— 「短いが完結した回答」まで機械的に深掘りしてしまうリスクがあり、まずはA案の効果を見てから検討
  - 却下: C案（プロンプトは変えず既定深掘り回数だけ引き上げ）— AIが「短くても答えになっていれば深掘りしない」と判断し続ける限り効果が薄いため
  - 維持: 「わからない」「特にない」への配慮（重ねて聞いても出てこないため深掘りしない）はそのまま。深掘り上限（調査ごとに設定可、既定2回・最大5回、`src/lib/follow-up.ts`）も変更なし。rating/nps質問はそもそも深掘り対象外（既存仕様のまま）
- 補足: ローカルの `OPENAI_API_KEY` がプレースホルダのため実際のgpt-4o応答での動作確認はできず、プロンプト文面のレビューのみで本番反映した。実際の会話での効果は本番での実施を通じて確認する

## 2026-08-12 スライド資料自動生成の認証方式を変更（サービスアカウント → 利用者ごとのOAuth）
- 背景: 「HJ専用ではなく、このツールを使う人なら誰でもスライドを作れる仕様にしたい」との指示。サービスアカウント＋HJの共有ドライブ方式は、生成したスライドがHJの共有ドライブに保存される前提のため、他組織のユーザーは閲覧・編集ができず「誰でも」を満たせないと判明
- 決定: **利用者ごとに自分のGoogleアカウントをOAuthで接続する方式（案B）に変更**。生成したスライドは接続した本人のGoogle Driveに保存される
  - 却下: 案A（PPTX自動生成に切り替え）— Googleアカウント不要でどの組織でも使えるが、今回は「Googleスライドとして生成・共同編集したい」という当初の要望を維持するため見送り
  - 却下: 案C（まずPPTXでリリースし後日OAuthを追加）— 二度手間になるため、最初からOAuth方式で実装する
- 影響: Google Cloud 側で**サービスアカウントではなく OAuth クライアントID（ウェブアプリケーション）を作成**する。すでに作成済みの Google Cloud プロジェクト・有効化済みの Slides API / Drive API はそのまま使う。サービスアカウントの作成手順（DECISIONS.md旧エントリの手順2〜4）は不要になった
  - スコープは `presentations`（Slides編集）・`drive.file`（アプリが作成したファイルのみアクセス。Drive全体への広いアクセス権は持たせない）・`userinfo.email`（接続中のアカウントを設定画面に表示するため）の3つ
  - トークン（refresh token）は User 単位で保存する。**平文では保存せず、`TOKEN_ENCRYPTION_KEY`（Claudeが生成しVercelに設定）でAES-256-GCM暗号化してから保存する**（push前レビューで指摘。特定組織専用ではなくなり外部利用者のトークンも預かることになるため、DB漏えい時の被害を一段小さくする）。接続状態はダッシュボードの設定画面から確認・解除できるようにする
  - OAuth 同意画面の設定（外部ユーザー向け、テストユーザー登録 or 本番公開）が新たに必要。テストモードは登録した100人までしか使えないため、社外の利用者が増える見込みなら早めに本番公開の検討が要る
- 実装済み: OAuth クライアントID 作成 → Client ID / Secret / TOKEN_ENCRYPTION_KEY を Vercel の環境変数に設定 → OAuth接続フロー（`/api/auth/google/connect` `/callback` `/disconnect` `/status`）とトークンの暗号化保存を実装。`/dashboard/settings/google` で接続・解除できる
- 次の作業: 当初計画していたスライド構成（表紙/サマリー/タスク成功率/タスク別詳細/満足度スコア/感情傾向/注目発言）の生成ロジックを実装（`getAuthorizedClientForUser` はまだどこからも呼ばれていない）

## 2026-08-12 スライド生成ロジックの仕様（枚数・ボタン・共有設定）
- 背景: スライド構成案（7枚固定）を提示したところ、「答えは調査内容による」との指摘。ある程度セッション数がこなせて初めて分析結果（AI総括・NPS等）が意味を持つため、調査によって出せる結論もあれば出せないものもあり、分量もヒアリングの濃度で変わるべき、という考え方
- 決定:
  1. **各セクションは「表示できるデータがある時だけ」出す固定枚数ではなく可変枚数**にする。「データなし」のプレースホルダースライドは作らない（発表資料に空スライドを混ぜたくないため、黙って省く）
     - サマリー: `commonInsights` が生成済み（セッション2件以上）のときだけ
     - タスク成功率・タスク別詳細: ユーザビリティテストで `overallSuccess` が算出できる（試行が1件以上ある）ときだけ
     - 満足度スコア: NPS/評価質問への回答が1件以上あるときだけ
     - 感情傾向: 感情データが1件以上あるときだけ
     - 注目発言: リサーチャーが付けたハイライトが1件以上あるときだけ
     - 表紙のみ常に出す
  2. **生成ボタンは調査詳細ページの右上**に置く
  3. **押すたびに毎回新しいファイルを作成**する（前回分の上書き・追記はしない。過去に生成した版を残せることを優先）
  4. **共有設定は自動で付与しない**。ファイルは作成した本人のみアクセスできる状態のままにし、共有したければ本人がGoogle Slides側で手動設定する（想定外の相手に自動公開されるリスクを避ける）

- 背景: EMU座標で図形（テキストボックス・矩形の棒グラフ・表）を手組みするネイティブGoogle Slides API方式を3回改善しても、「デザインが簡素すぎる」という指摘が解消しなかった。Gamma/Canva等の有償AIスライド生成サービスやNotebookLMは、API連携（CanvaはEnterprise限定）や公開APIの不在で採用できないと判断

  - 却下: 案A（ネイティブSlides図形のまま改善を続ける）— EMU手計算の設計の限界に達しており、これ以上の作り込みでも見た目の天井は変わらないと判断

  - タスク別詳細テーブルの行数上限（旧実装にあった MAX_TABLE_ROWS=12 + 「ほか N件」要約行）が画像化への書き換えで一度失われていたが、push前レビューで検出し復元した

## 2026-07-31 参加前チェック（プリフライト）
- 背景: 参加ページは「カメラ・マイクが必要です」と**文章で伝えるだけ**で、実際に動くかは確かめていなかった。音が聞こえない・小窓が開かない・画面録画で「タブ」を選んでしまう、はいずれも**テスト開始後に初めて発覚**し、そのセッションは作り直せない。ブラウザ判定も「音声認識が無い場合（Brave 等）」だけで、Safari は素通りして service モードで破綻していた
- 決定（ユーザーが3点とも確定）:
  1. **範囲はフル**。共通4ステップ（ブラウザ／カメラ／マイク／音声の再生）＋ service モードのみ追加2ステップ（小窓／画面録画）。使わない機能の欠落では弾かない（プロトタイプテストに画面録画は要らない）
  2. **完全ブロック**。すべて OK にならないと先へ進めない
  3. **参加前（名前入力の前）に置く**。参加できない人の空セッションが作られず、集計が汚れない
- 実装の要点:
  - 判定ロジックは `src/lib/preflight.ts` に純関数として切り出し、単体テスト35件で固定（音・カメラ・画面共有は preview で動かせないため）
  - マイクは **100ms × 3フレーム連続**で発話とみなす。requestAnimationFrame（約16ms）だと3フレームが50msにしかならず、打鍵音ひとつで合格してしまう
  - 顔の位置判定は実行中の警告と**同じ規則**にする（事前に OK だったのに開始直後に警告が出ると直しようがない）
  - 画面共有は `displaySurface` が `monitor` 以外なら「画面全体を選んでください」とやり直させる。ただし**報告されないブラウザでは通す**（確かめようがない理由で参加を断らない）
  - カメラ・マイクの許可はオリジンに残るので、テスト画面では再確認されない。ページ遷移前にトラックを停止する（カメラのランプが点いたままにならないように）
- **顔の位置だけは完全ブロックから外した（同日、ユーザーが決定）**: カメラが映ることは必須のままだが、顔の位置は警告にとどめる。暗い場所などで検出が失敗し続けると参加者側に直しようがなく、その人を確実に失うため
  - **8秒の猶予（`FACE_GRACE_MS`）が過ぎてから**「うまく認識されないので、このまま進む」を出す。すぐ出すと、カメラを直せる人まで押してしまいチェックの意味が無くなる。顔が写っている人にはこの逃げ道を見せない
  - 判定は `cameraGate()` に切り出してテストで固定した（主ボタンを出す条件と、逃げ道を出す条件を別々に持つ）
  - 保留: 逃げ道を使ったことをセッションに記録するか（表情データが当てにならない参加者を後から見分けられる）。`Session` に列が要りスキーマ変更になるので、必要になってから
- 完全ブロックの副作用として残るリスク（要観察）:
  - Safari / Firefox の参加者は 100% 参加できない。従来の「テキスト入力で続ける」フォールバック（`textOnlyMode`）は残すが、新規の参加動線は必ずこのチェックを通るので実質使われない
  - `/api/tts` が落ちているときは確認音（ビープ）に切り替えて通す。サーバー側の一時的な不調で参加そのものを止めないため

## 2026-07-31 参加者からの質問への対応
- 背景: タスク中は音声認識を動かしていないため、参加者が「どこを押せばいいんですか？」と聞いても**誰にも届かず無反応**。さらに質問して黙ると20秒後に思考発話の促しが出るので、「質問を無視して話を促す」並びになっていた
- 前提（ユーザビリティテストの作法）: 操作・仕様の質問には答えない（答えると「自分で見つけられるか」を測れなくなる）。一方でテストの進め方の質問には答えるべきで、放置すると測っているものが「テストの分かりにくさ」に変わる
- 決定: **B案（先に伝えるだけ。実装最小）**
  1. ガイド画面に「テスト中は操作方法などのご質問にお答えできません」と**理由つきで**明記する（理由を書かないと不親切に読める）
  2. 最初のタスク読み上げの冒頭で、思考発話のお願いと一緒に一度だけ声でも伝える
  3. それ以上の仕組み（質問ボタン・質問の記録・終了時の質問欄）は作らない
- 却下: 案A（小窓に「質問がある」ボタン＋定型の返し＋終了画面の質問欄＋記録）— 同じ質問が複数人から出れば発見になる（例: 3人が「これは保存されますか」と聞く＝表示が足りない）ので価値はあるが、今回は最小で様子を見る。**必要になったらここから再開する**
- 却下: 案C（タスク中も音声認識を回して AI が応答）— 背面タブで認識が止まる（service モードのメイン画面は背面）、AI が操作方法を教えてしまうと測定が壊れる、費用も増える
- 文言は「答えない」ではなく**「あとで聞く」**にする（レビュー指摘）。明確に拒否すると「話しても無駄」と学習されて思考発話そのものが減る。事後インタビューは実在するので嘘にならない。また**範囲は「操作方法などの」に限定**する。無修飾で「ご質問にお答えできません」と言うと、参加者が進行上の困りごと（小窓が消えた・録画が止まった気がする）まで諦めて黙り、そのセッションが測るのはサービスの使いやすさではなくツールの分かりにくさになる
- 残る制約:
  - 質問しても無反応であること自体は変わらない。伝えることで「答えが返る」期待を減らすだけ。参加者が質問した直後に思考発話の促しが出る可能性も残る（発話でタイマーは一度リセットされるので、直後ではなく20秒後）
  - **タスク1の所要時間には冒頭の教示（約12秒）が含まれる**。計測開始は読み上げ開始と同時なので、タスク1だけ系統的に長く出る。参加者間の比較は同条件なので壊れないが、**タスク間の比較**では誤読しうる（直すなら「読み上げ完了後に計測を開始する」という別スコープの変更になる）
  - この教示は文字起こしに残らない（`log: false`）。届いていたかを後から確認する手段は録画音声だけ

## 2026-07-29 思考発話（think-aloud）を促す
- 背景: 思考発話がないと、迷った理由や期待とのズレが分からない。促す仕組みは無く、タスク中は音声認識も動いていない（発話は録画の音声にだけ残り、テキストにするには手動の再文字起こしが必要）

  4. 他の案内（詰まったときの声かけ・立て直し手順・SEQ入力中）が出ている間は促さない。画面に2枚重ねると、どちらも読まれなくなる
  5. 開始時のお願いは「ガイド画面の流れ」に加えて、**最初のタスク読み上げの冒頭で一度だけ**声に出す（毎回言うと聞き流される）
  6. 沈黙検知は**メイン画面と小窓のどちらか一方だけ**が動かす（小窓が生きていれば小窓、prototype モードとフォールバックはメイン画面）。両方で動かすと同じ沈黙に二重で声をかける
  7. 促しの発言は文字起こしに残す（タスク読み上げと違い、促されて話したのか自発的に話したのかで発言の重みが変わるため）
- 却下: 音声認識（SpeechRecognition）で判定 — 背面タブで止められることがあり、service モードのメイン画面は背面になる。何を話したかは不要で「話しているか」だけで足りる
- 却下: 案B（常時リマインダーのみ）— 数十秒で慣れて無視され、黙り込んだ人に効かない。ただし「開始時に一度お願いする」部分は採用した
- 却下: 案C（練習タスクでウォームアップ）— 効果は最も高いが「練習タスクを集計から外す」仕組みが別途必要でスコープが大きい。必要になったら改めて
- 判定ロジック（いつ促すか・発話とみなす音量）は `src/lib/think-aloud.ts` に純関数として切り出し、単体テストで固定した。音の入出力は preview では検証できないため
- **読み上げ中は沈黙として数えない**（レビューで判明）。マイクは既定で echoCancellation が有効なので、自分の読み上げ音声はマイク信号から除去される＝読み上げ中も「沈黙」に見える。放置すると長いタスク文の20秒目に促しが割り込み、`speak()` が読み上げをキャンセルしてタスクの後半が聞けなくなる。メインは `isSpeaking`、小窓は `tts_state` の通知で止め、読み上げが終わった時点から20秒を数え直す
- 促しが出ないときに疑う場所（レビューで挙がった既知の制約）:
  - クリック音やキー入力が連続2フレーム（約400ms）続くと「発話」と判定される。しきい値は RMS 0.012
  - 「詰まっていませんか」の声かけが一度出ると、そのタスクでは促しが止まる（案内を2枚重ねないため）
  - service モードで小窓がブロックされ、かつサービスURL未設定だと着手の合図（`markFirstTaskStart`）が発生せず、読み上げ・声かけ・促しのすべてが起動しない（従来からの穴）
- 保留: 促した発話をテキストで読めるようにするか（ユーザビリティのセッションで自動 Whisper 文字起こし）。Whisper は話者分離ができずセグメントを全置換するので、事後インタビューの「AI／参加者」の区別が失われる。**実際に発話が増えたのを見てから決める**

## 2026-07-29 ユーザビリティテストのタスクを読み上げる
- 背景: 事後インタビューの質問は TTS で読み上げるのに、タスクフェーズは無音でテキストのみだった（`InterviewRoom.tsx` に「タスクフェーズへ（TTS なし）」）。service モードの参加者は別タブでサービスを操作しているため、タスクを読むたびに小窓へ視線を戻す必要があり、その動作自体がテストのノイズになる。本来のユーザビリティテストではモデレーターがタスクを読み上げる
- 決定: **A案（タスク表示時に自動で読み上げ＋「もう一度聞く」ボタン）**
  1. タスクが表示された時点（着手できる時点）と、タスクが切り替わるたびに1回読み上げる。読み上げ文は「タスクN。〈文言〉」
  2. テキスト表示は残す（音声だけにすると記憶に頼らせることになる）
  3. 小窓とメイン画面に「もう一度聞く」ボタンを置く。音声はメイン画面側（`speak()` の持ち主）で鳴らし、小窓からは BroadcastChannel で依頼する
  4. **読み上げは文字起こしに残さない**。タスク文言は結果記録（`タスク1「…」→ 達成`）で既に残っており、Interviewer の発言として二重に入れると AI の回答抽出・要約がタスク文を質問として扱いうる
  5. ヒント・立て直し手順は今回の対象外（まずタスク文言だけに絞る）
- 却下: 案B（ボタンだけ置いて自動再生しない）— 押さない人には届かず、受ける助けが人によって変わる＝参加者間の比較可能性が落ちる
- 注意: 自動再生がブラウザに止められた場合は既存の `speak()` と同じく通知を出すが、その通知はメイン画面に出る（参加者はサービスのタブを見ている）。小窓にタスク文が常に見えていることと、「もう一度聞く」で再試行できることで担保する
- **`log: false` が効くのはライブの文字起こしだけ**（レビューで判明）。読み上げ音声はスピーカー→マイク経由で録画に入るため、リサーチャーが「再文字起こし」を実行すると Whisper が拾い、話者不明の発言としてタスク文が復活する。そこから回答抽出を走らせるとタスク文が回答として抽出されうる。質問の読み上げも以前から同じ性質なので許容するが、「回答にタスク文が混ざっている」を見たらこの経路を疑う
- 補足: 小窓からの「もう一度聞く」はタスク中のみ受け付ける。`speak()` は再生中の音声をキャンセルするので、事後インタビューの質問を途中で切ると回答の聞き取り開始（onEnd）が失われて進行が止まる

## 2026-07-29 地続きのタスク（前提タスク）で断念した人の扱い
- 背景: タスク1「お気に入りに追加」→ タスク2「お気に入りから〇〇する」のように後続が前のタスクの結果を必要とする場合、1で断念した参加者は2を**物理的に始められない**。従来は断念すると即座に次へ進み、2は「断念」として記録されていた＝「やってみて出来なかった」と「そもそも始められなかった」が同じ成功率に混ざっていた
- 決定: **A案（前提状態への案内を出して、後続タスクは通常どおり測る）**
  1. タスクに「**このタスクは次のタスクの前提になる**」印（`Task.isPrerequisite`）を追加
  2. 前提タスクのヒント欄は「立て直し手順」も兼ねる（答えそのものを書く運用。ラベルと補足文でそう促す）。ヒントは達成を助けるためだけでなく、**断念した人を次の開始地点まで連れて行くため**にも使う
  3. 前提タスクで「できなかった」が押されたら**自動で次へ進めず**、立て直し画面を出す。「準備できた→次へ」／「この状態にできない」の2択
  4. タスク1は**断念のまま記録**する（助けたから成功にはしない）。次のタスクには `TaskResult.assistedStart` の印を付ける
  5. 立て直せなかった場合は後続を `outcome: 'not_attempted'`（未実施）で記録。前提の印が連鎖している間は続けて未実施にし、印が切れたところから再開する
  6. 集計では未実施を**試行回数（分母）から除外**し、「未実施 N件」として別表示する。`assistedStart` も `usedHint` と同じ思想で別カウント（既存の「自力成功」の定義には混ぜない）
- 却下: 案B（テストデータを仕込んで依存を消す）— 「追加してから使う」一連の流れ自体を見たい場合に測れない。ただし A と排他ではなく、流れが目的でないタスクは運用でこちらを選べばよい
- 却下: 案C（前提タスクで断念したら以降を打ち切る）— 数字は正直だが、その参加者から後続画面の発見が一切取れない
- 補足: 前提を代行して開始した参加者は「お気に入り追加のUIを教えられた状態」で後続に入るため、自力で到達した人と厳密には同条件ではない。だから印を残して集計で分けられるようにする（混ぜると実態とズレる）

## 2026-07-28 質問×被験者の回答比較テーブル
- 背景: 「質問1を肯定的に回答した人／そうでない人を見分けたい」。深掘り質問は人によって個数が違うが、元の質問に紐づいているはず、という指摘
- 前提の確認: 深掘りの回答は `recordOpenAnswerIfAny` が元の質問の Answer 1件にまとめて保存している（questionId で紐づく）。したがって列は人によって増減しない
- 決定: インタビュー詳細に「回答の比較（質問 × 参加者）」テーブルを追加。行=参加者・列=質問。参加者列は固定、列ヘッダで並び替え、回答本文での絞り込み、スコアは色分け、長文は展開
  - セルの対応づけは questionId が第一キー（質問を並べ替えても崩れない）。questionId を失った回答は文言で拾うが、1件の回答を複数列に出さないよう2周に分けて割り当てる
  - スコアの色分けは、NPS だけ標準区分（推奨者9-10／中立者7-8／批判者0-6）に合わせる。単純な比率だと 8 が肯定的に見え、同じ画面の NPS 集計と食い違うため
  - `Answer.followUpCount` を追加。発話数から数えると「深掘りされたが答えなかった」分が抜けるため、AI 側のカウンタ（followUpCountRef）の値を保存する
- 追記(2026-07-28): 自由回答にも AI 判定を追加（案B を選択）。`Answer.sentiment` に positive/neutral/negative を保存し、テーブルでバッジ＋色帯表示・判定順ソート・「肯定的」等での絞り込みに対応
  - 文字起こし分析とは**別の AI 呼び出し**にした（同じ呼び出しに混ぜると上限超過で要約まで壊れた前例があるため）。判定が失敗しても要約・テーマは無傷
  - 判定は「評価対象への態度」を見る（一般的な機嫌ではない）。AI 判定である旨を画面に明示し、参考値として扱う
  - 応答のパース失敗は「判定なし」ではなく**失敗として投げる**。同一視すると既存の判定を全件 null で上書きしてしまうため
  - 判定処理は `status: 'done'` の**後**に置く。前に置くと、ここで落ちたときに status が processing のまま固まり、画面から再分析できなくなる

  - CSV は測定結果セクションを先頭に追加し、全列を数式インジェクション対策の `q()` 経由に
- 却下: 文字起こしテキストを正規表現でパースして集計 — 書式変更や再文字起こしで壊れるため
- 補足: 経過時間の基準を「開始ボタン押下時」にリセット。従来はマウント時基準でガイド滞在時間が所要時間に混入し、録画の再生位置ともズレていた（文字起こし・感情・録画の3つの原点が揃うようになった）
- 所要時間の計測開始（タスク1）: 事前手続きの時間を含めないよう、被験者が実際に着手できる時点まで遅らせる。service=小窓から `task_ready`（録画開始＋サイトを開いた時点）を受信時／prototype=画面選択ダイアログが閉じた後／小窓が開けなかったフォールバック=メイン画面の「サービスを開く」クリック時。タスク2以降は前タスクの終了時刻を開始時刻とする
- 残課題（UXレビューの P1 以降）: 文字起こしの全文検索、タグ付け/ハイライト、横断エクスポート、発言単位 sentiment の修正（現状は全体の1値を全発言にコピーしていて誤解を招く）、調査の編集機能

## 2026-07-27 顔フレーミング判定（テスト中の見切れアラート）
- 決定: 小窓のカメラ映像に対し、tiny_face_detector（既存 /models、約190KB）で2.5秒ごとに顔検出し、**「顔が写っていない」「顔が画面端で見切れている」の2つ**を検知したら小窓のカメラ下端に警告バナーを出す。判定・表示は小窓で行う（被験者が見ているのは常に最前面の小窓／背面タブは処理が間引かれ検出不安定なため）
- 却下: 距離（遠い/近い）も警告 — 閾値調整が要り誤検知が増えるため見送り
- 却下: 見切れ時間帯を結果に記録 — スコープ拡大のため今回はライブ警告のみ
- 補足: 感情分析用の faceExpressionNet は読まず tinyFaceDetector のみロード（軽量化）。見切れ=顔 boxが映像端±1.5%に接触で判定。補助機能なのでモデルロード失敗時も録画は継続
- 適用範囲拡大(2026-07-27): 小窓だけでなく全モードに適用。メイン画面のカメラ（プロトタイプ時=右下の小型PiP／通常インタビュー時=全画面）にも同じ警告を表示。メインは既存 useEmotionDetection の感情検出ループ（5秒ごと）から顔 box を算出して二重処理を回避（小窓は独立ルートなので2.5秒の専用ループ）。バナー位置はカメラ映像の位置（PiP/全画面）に追従

## 2026-07-28 prisma は db push 方式に統一（マイグレーション削除）
- 背景: schema.prisma は postgresql、`prisma/migrations` は sqlite という矛盾が未解決だった
- 実態調査: 残っていたマイグレーションはテーブル 7 個ぶんのみで、現在のスキーマ（17 モデル）を再現できない。lock も sqlite のまま。デプロイは `prisma db push --accept-data-loss`（build スクリプト）で行っており、マイグレーションは一切使われていなかった
- 決定: `prisma/migrations` を削除し、**db push 方式であることを schema.prisma の冒頭に明記**する。`prisma migrate` を実行すると失敗するか壊れた DB ができる罠だったため
- 却下: 稼働中DBから baseline を作って migrate 方式へ移行 — 動いている本番のデプロイ経路を変えるリスクが大きく、現状の運用規模に見合わないため。将来必要になった時点で baseline から始める
- 補足: `prisma/dev.db`（SQLite 時代の残骸）は .gitignore 済みでリポジトリには入っていない
