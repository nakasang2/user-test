### AI 出力の扱い
- 2026-07-28 | 一括処理の「5件ずつ」実装で、開始位置（skip）を持たせずに毎回先頭N件を処理していた。UIが「残りN件、もう一度実行してください」と案内するのに、押しても同じ5件を再処理し6件目以降が永久に処理されない（push前レビューで検出）→ **バッチ処理は「対象が処理後に減る」設計か「開始位置を進める」設計かをはっきりさせる**。前者を前提にするなら、対象から外れる条件をUIの呼び出しでも満たしているか確認する
- 2026-07-28 | 初回分析と再分析で同じ関数を使い回したため、AI失敗時の「分析に失敗しました。」保存が再分析でも走り、既にある良い要約・テーマ・感情判定を不可逆に破壊する設計だった（push前レビューで検出）→ **「まだ何も無い初回」と「既に良いデータがある再実行」では失敗時の扱いが逆になる**。共通化するときは失敗時の挙動を呼び出し側で選べるようにする
- 2026-07-28 | AI 応答のパース失敗時に空マップを返していたため、呼び出し側が「1件も判定できなかった」と解釈して既存の判定を全件 null で上書きする設計になっていた（push前レビューで検出）→ **「失敗」と「結果ゼロ」は別物として扱う。失敗は例外で伝え、呼び出し側に既存データを保持させる**
- 2026-07-28 | 追加の AI 呼び出しを `status: 'done'` の前に挿入したため、そこで落ちると status が processing のまま固まり、画面の「再分析」ボタンが出ずに復旧不能になる経路を作っていた → **補助的な処理は主処理の完了フラグを立てた後に置く**。長時間化する API には `maxDuration` を明示する
- 2026-07-28 | AI の分析結果に「失敗時のフォールバック値」を入れていたため、分析が失敗しても画面上は判定できたように見えていた（sentiment のフォールバックが `'neutral'`）→ **判定不能と判定結果は区別する。失敗時は null にして UI で非表示にする**。同様に、全体の値を個別項目にコピーして埋めるのは「実態のないデータの捏造」であり、リサーチツールでは誤った意思決定に直結する
- 2026-07-28 | AI に配列（発言ごとの判定）を返させたことで出力が発言数に比例して伸び、max_tokens 超過で JSON が壊れると要約ごと全損する構造だった（push前レビューで検出）→ **可変長の出力を求めるときは上限を発言数の最大ケースで見積もり、`finish_reason === 'length'` を検知してログに残す**
- 2026-07-28 | AI が返す index で配列を引く設計にしたが、ずれた場合に無検出だった → **AI が返す添字は信用せず、突き合わせ可能な属性（話者など）でサーバー側で検証する**

### データ設計
- 2026-07-28 | 新しいテーブルを前提にした機能を作ったが、既存データにはその行が無いため画面に何も出ず「機能が無い」ように見えた → **スキーマを増やす機能では、既存データがどう見えるかを必ず確認する**。空のときは黙って消さず理由を出し、必要なら移行（バックフィル）の導線を用意する
- 2026-07-28 | バックフィル処理で、対象選定（SELECT）と書き込みの間に数分の AI 呼び出しが挟まり、その間に本物のデータが書かれると上書きする競合があった（push前レビューで検出）→ **後追いでデータを埋める処理は upsert ではなく「既存行はスキップ」で書く**。長い処理を挟む場合、選定時点の判断は書き込み時には古い
- 2026-07-28 | 「集計から除外するフラグ」を追加した際、除外を入れたつもりの箇所が実は画面で使われておらず（`_count` を足したが JSX は別APIの値を表示していた）、ダッシュボードだけ数字が食い違った（push前レビューで検出）→ **除外フラグを足したら「そのAPIの値が実際に描画されているか」まで確認する**。同じ数字を複数の経路で算出している画面があると、片方だけ直して矛盾が生まれる
- 2026-07-28 | 調査の編集機能を入れたら、タスクを並べ替えるだけで横断集計が別タスクと合算される設計だった（push前レビューで検出）→ 集計のグループ化キーに `order`（表示順）を使っていた。order は編集のたびに振り直されるため、同じ order が別項目を指すようになる → **集計キーには表示順ではなく安定ID（taskId / questionId）を使う。無い場合のフォールバックは文言**。「並び順」は表示のためだけに使う
- 2026-07-28 | ユーザビリティテストなのにタスク成功率もNPSも集計できなかった → **測定結果を「表示用のテキスト」として文字起こしに混ぜて保存していた**（`タスク1「…」→ 達成` / `9（9 / 10）`）。設問（Task/Question）のテーブルはあるのに回答のテーブルが無かった → **ユーザーに見せる文言と、集計に使う値は別に保存する**。「あとで数える必要がある値」は最初から専用テーブルに数値で持つ
- 2026-07-28 | 並行リクエストで結果が重複・巻き戻る設計になっていた（push前レビューで検出） → クライアントが毎回全件送信し、サーバーが deleteMany→createMany する「全置換」方式にしていた。順序保証も一意制約も無いため、遅延した古いスナップショットが新しい結果を消す／READ COMMITTED 下で両方の行が残る → **自然キー（sessionId+order）に unique 制約を張り、行単位 upsert にする**。全置換は「クライアントの手元が常に完全」という前提が要り、リロード・二重送信で崩れる
