# data-model-review — 集計・データ設計のチェックリスト

## なぜこのスキルがあるか

このリポジトリでは、集計とデータ保存の設計ミスが**リサーチャーに誤った結論を出させる**バグとして
繰り返し現れた。いずれも「作った直後の1件だけ見れば正しい」ため、実装時には気づけない。

## 実装前・変更前に必ず確認する

### 1. 「あとで数える値」を表示用テキストに混ぜていないか
集計に使う値は、専用のテーブル・カラムに**数値のまま**持つ。

過去の事故: タスクの成否を文字起こしに `タスク1「…」→ 達成` という文章で保存し、
評価を `9（9 / 10）` という発言として保存していた。設問のテーブルはあるのに回答のテーブルが無く、
**成功率も NPS も原理的に集計できなかった**。

- ユーザーに見せる文言と、集計に使う値は**別に保存する**
- 文字起こしのように再生成・再文字起こしで置き換わるものに、集計対象を混ぜない

### 2. 集計のグループ化キーに「表示順」を使っていないか
`order` は編集で振り直される。同じ order が別の項目を指すようになり、**別項目の結果が合算される**。

```ts
// NG: 表示順でまとめる
const key = t.order

// OK: 安定IDでまとめ、無い場合は文言でフォールバック
const key = t.taskId ?? `text:${t.text}`
```
表示順は**並べ替えの表示のためだけ**に使う（`Math.min` で代表値を取る等）。

### 3. 「全置換」で保存していないか
クライアントが全件送信し、サーバーが `deleteMany` → `createMany` する方式は、
「クライアントの手元が常に完全」という前提が要る。リロード・二重送信・並行送信で崩れる。

- 自然キー（例: `sessionId + order`）に **unique 制約**を張る
- **行単位の upsert** にする（遅延した古いリクエストは同じ行に同じ値を書くだけ）

### 4. 後から埋める処理（バックフィル）で既存行を上書きしていないか
対象選定（SELECT）と書き込みの間に AI 呼び出しなど数分の処理が挟まると、
その間に**本物のデータが書かれていても上書きしてしまう**。

- `upsert` ではなく `createMany({ skipDuplicates: true })`（既存行は触らない）
- 実施中（`pending` / `active`）のレコードは対象から外す

### 5. 「集計から除外するフラグ」を足したら、描画経路まで確認したか
過去の事故: `_count` にフィルタを足したが、画面はその値を使っておらず**別 API の自前集計を表示**していた。
結果、同じプロダクト内で件数が食い違った。

- 同じ数字を複数の経路で算出している画面が無いか探す
- 足したフィルタが**実際に描画されている値**に効いているか確認する
- 除外の抜け漏れをリポジトリ横断で確認する（検索・エクスポート・AI文脈・各種件数）

### 6. 新しいテーブルを前提にした機能で、既存データがどう見えるか確認したか
既存レコードにはその行が無いので、画面に何も出ず「機能が無い」ように見える。

- 空のときは**黙って消さず理由を出す**
- 必要なら移行（バックフィル）の導線を用意する
- 導線は「1件でも埋まると消える」場所に置かない（残りを埋められなくなる）

### 7. スキーマ変更の反映方法を守っているか
このリポジトリは **`prisma db push` 方式**（`package.json` の build）。`migrations` は置かない。
詳細は `prisma/schema.prisma` 冒頭のコメントを参照。

- 追加のみ（新テーブル・NULL 許容カラム）なら既存データは無事
- unique 制約の追加は、既存に重複行があると失敗する

## レビュー時の観点（他人の変更を見るとき）

- 2件目・3件目を入れたらどうなる？（1件だけなら大抵正しく見える）
- 項目を並べ替え・削除したら集計はどうなる？
- 同時に2つ書き込まれたら？ リロードしてから続けたら？
- 既存データ（その機能より前のレコード）ではどう見える？
