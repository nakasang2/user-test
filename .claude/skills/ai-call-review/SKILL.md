# ai-call-review — AI 呼び出しのチェックリスト

## なぜこのスキルがあるか

このリポジトリで起きた**データ破壊級のバグは、そのほとんどが AI 呼び出しの周辺**から出ている。
いずれも「AI が期待どおり返ってきたとき」は正しく動き、**失敗経路と再実行のときだけ壊れる**ため、
実装直後の動作確認では気づけない。以下は実際に本番前レビューで見つかった事故のパターン。

## 実装前・変更前に必ず確認する

### 1. 「失敗」と「結果ゼロ」を混同していないか
AI 応答のパースに失敗したとき、空の結果（`{}` / `[]`）を返してはいけない。
呼び出し側が「1件も該当しなかった」と解釈し、**既存データを空で上書きする**。

```ts
// NG: 失敗を「結果ゼロ」として返す
catch { return {} }

// OK: 失敗は例外で伝え、呼び出し側に既存データを保持させる
catch { throw new Error('[fn] 応答が JSON として読めませんでした') }
```

### 2. フォールバック値で「判定できたように見せて」いないか
失敗時に `'neutral'` や `0` のような妥当そうな値を入れると、画面上は正常に見える。
**判定不能と判定結果は必ず区別し、失敗時は null にして UI で非表示にする。**
全体の値を個別項目にコピーして埋めるのも同じ問題（実態のないデータの捏造）。

### 3. 初回と再実行で失敗時の扱いが逆になっていないか
- **初回**（まだ何も無い）: 失敗を保存して見せるほうが分かりやすい
- **再実行**（既に良いデータがある）: 何も書かずに中断する。上書きは不可逆な破壊

共通関数にするなら、失敗時の挙動を**呼び出し側で選べるように**する
（例: `onAnalysisFailure?: 'fallback' | 'abort'`）。

### 4. AI が返す添字・ID を信用していないか
`{i: 3, s: "..."}` のような添字で配列を引く設計は、AI がずれた値を返すと無検出で壊れる。
- 送った範囲内かを検証する（`idx < sent.length`。`items.length` ではなく**実際に送った件数**）
- 突き合わせ可能な属性（話者・型など）でサーバー側でも検証する

### 5. 可変長出力の上限を見積もったか
発言数・件数に比例して出力が伸びる設計（配列で返させる）は、`max_tokens` を超えると
JSON が壊れて**同じ応答に含まれる要約なども全損する**。
- 最大ケースで見積もる（整形 JSON は1件あたり 20 トークン強）
- `finish_reason === 'length'` を検知してログに残す
- 出力が長くなるものは**別の呼び出しに分ける**（片方の失敗が他方を壊さない）

### 6. 補助的な処理を主処理の完了フラグより前に置いていないか
`status: 'processing'` → AI 呼び出し → `status: 'done'` の順で書くと、
補助的な AI 呼び出しがそこで落ちたとき **status が processing のまま固まる**。
画面から復旧できなくなるので、**完了フラグを立てた後に補助処理を置く**。

### 7. 長時間化する API に maxDuration を明示したか
AI を複数回呼ぶ API は既定の実行時間上限では足りない。
```ts
export const maxDuration = 300
```
一括処理なら、**次の1件に着手する前に**残り時間を見る（着手後に強制終了されると status が残る）。

### 8. 一括処理の進み方を決めたか
「N件ずつ、残りは再実行」の設計には2通りある。混ぜると取り残しが出る。
- **対象が処理後に減る**: 処理済みが条件から外れる（例: 日本語化されたら対象外）
- **開始位置を進める**: `skip` を受け取り、呼び出し側が進める

後者を選ぶなら、UI 側で `skip` を実際に渡しているかまで確認する。
UI が「残りN件、もう一度実行してください」と案内するなら、押して本当に進むかを検算する。

### 9. プロンプトの言語を指定したか
system プロンプトが英語だと、出力も英語になる。日本語で使うツールなら明示的に指定する。
分割処理がある項目（カンマ区切りのテーマなど）は**区切り文字も指定**する（「、」になると壊れる）。

### 10. 未認証エンドポイントならレート制限を付けたか
AI 呼び出しはコストが直接発生する。認証の無い経路では必須。

## レビュー時の観点（他人の変更を見るとき）

- 失敗経路を追う: AI が例外を投げたら？ 壊れた JSON を返したら？ 上限で切れたら？
- 再実行を追う: 2回目・3回目に押したらどうなる？ 既存データは守られる？
- 並行を追う: 実施中のセッションが対象に入る？ その間に本物のデータが書かれたら？
